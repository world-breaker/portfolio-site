0 · 总览：六个项目怎么串成一条链

你这套作品集不是六个孤立 demo，而是一条递进的能力链：把"检索"做成可复用服务 → 被 Agent 调用 → 全链路可观测 → 用评测平台量化效果 → 把零件拼成真能用的应用 → 再从零训一次小模型把基本功也证明一遍。面试时讲清这条主线，比逐个罗列项目强十倍。

一句话主线：检索（rag-mcp-server）→ 被 Agent 调用（hello-agent）→ 用评测平台量化（rag-eval-platform）；interview-assistant 是同类 RAG 思想的「产品化」落地（本地多角色对话）；job-fit-assistant 是把三个地基「拼成应用」的落点（求职助手）；tiny-llm-from-scratch 是另一条独立支线——不用任何预训练权重，从数据到分词器到训练到评测自己走一遍。
再加一层（本版补齐）：把零件拼成真能用的应用（求职助手：12 份 JD × 4 份简历的客观评测，含「纯 LLM 抽取反而不如关键词基线」这种负结果），并把基本功自己走一遍（从零训一个 15.59M 的小模型，val PPL 36.47，优于 bigram 基线 7.68×）；把服务做成「可运维、可审计」，把 Agent 做成「可中断、可核算」——鉴权 / 限流 / 探针 / 指标 / 注入防护，断点续跑 / 用量与成本；并且每一项都能用一条命令现场跑给你看。

LangGraph韧性可观测量化评测并发 + 记忆 + 压缩断点续跑(新)用量核算(新)

一句话：用 LangGraph 手写"模型思考 → 调工具 → 看结果 → 再思考"循环，并给循环装上三道工程护栏：最大步数、失败重试/降级/熔断、全链路 JSONL trace。状态只有三个字段，循环只有两个节点。

关键设计决策（面试加分点）

决策为什么
手写 StateGraph，不用 create_react_agent框架封装掉的"步数怎么数 / 错误怎么回灌 / 状态放哪"正是面试考点；手写约 100 行换来确定性与可讲性
失败分四档：permanent 不重试 / retryable 退避重试 / 耗尽降级 / 连败熔断把"概率性失败"变成确定性处置；未知异常一律按 retryable（多试一次的代价 < 直接放弃）
RAG 工具双形态：MCP 客户端优先，连不上降级进程内直连进程隔离（BGE 不进 Agent 进程）+ 复用给 Cursor/Claude；两条路径返回同一 JSON 契约，模型无感知
trace 一次任务一个 JSONL，密钥永远 sk-****可回放、可 jq 统计；有测试守着"密钥不泄漏"红线

新增：量化评测（把"我跑了 3 条 demo"升级成硬指标）

新增文件（不改既有代码）：agent/eval_harness.py + scripts/eval_agent.py + data/eval_queries.json(16 条) + tests/test_eval_harness.py(4 单测全过)。
直接复用 run_task 返回的 metrics（tool_success_rate / 重试 / 降级 / 熔断）并从 trace 抽工具名，聚合成：完成率、平均步数、平均工具成功率、工具选择准确率、失败恢复率、领域外诚实率。其中两处口径是我审计自己指标时改掉的：工具选择准确率拆成严/宽双口径（严＝工具真的成功执行过、宽＝只是发起过——原口径把"尝试过但全失败"也算选对，指标虚高）；领域外诚实率只统计真正完成的运行，并把分母（完成条数 / 领域外总条数）一起报出来——原来的口径会把"模型调用失败、什么都没答出来"的兜底文案当成"诚实拒答"，诚实率能刷到 1.0（典型的假绿，已修并有回归单测锁住）。
运行：.venv\Scripts\python.exe scripts\eval_agent.py --rag-mode direct（需 .env 端点）。跑完落 eval_results/eval_*.md。

增强：工具并发化 + 跨任务记忆

并发化：模型一轮可能同时要「查知识库 + 算数 + 取时间」，串行会把延迟累加。用 asyncio.gather 并发，总延迟 ≈ 最慢的那个；Semaphore 限并发，gather 保序保证 ToolMessage 与 tool_calls 一一对应。实测 4 个 0.2s 工具：并发 0.2s vs 串行 0.8s，有测试断言顺序与耗时。
跨任务记忆：单次 messages 任务结束就丢。新增 agent/memory.py：JSONL 落盘、同 key 覆盖、BM25 召回（idf 让稀有词权重更高、b 做文档长度归一化；可切回 overlap 做 A/B）；任务启动只注入与任务相关的 top-k，无重叠不注入；remember_fact 拒绝疑似密钥。
上下文压缩：每步送模型前把历史压到字符预算内——只压内容、不删消息，保住 tool_call_id 配对；18 条消息 2643 → 1824 字符（-31%）。
在上一轮测试基础上再加 BM25、上下文压缩，以及本版新增的 checkpoint 续跑与用量核算用例后，全量 180 passed / 1 skipped，零回归。离线演示：scripts/demo_memory.py。

本版新增：断点续跑（checkpoint）+ 用量与成本核算

把「跑到一半进程被 kill 就白跑」变成可续跑：checkpoint 后端可切——官方 sqlite saver 与自研 JSONL 双后端；命令行 --thread-id 指定会话、--resume 续跑。
硬证据（scripts/demo_resume.py，离线可复现）："进程被杀"是用脚本化假模型 + 一个抛 BaseException 的工具造出来的（ToolExecutor 只兜 Exception，所以它直接逃出 run_task，等价于进程结束），然后换一个新的 checkpointer 实例（模拟新进程）用同一个 thread_id 再跑一次。结果：calculator 调用 1→1（没被重放）、只补跑失败的那一步、模型调用 2→1（没把前面两步重算）、最终 status=completed、重放步数 = 0。
用量与成本核算：扫 trace 重算 token 与费用（单价表可配），实测汇总 12 次真实运行 / 49,635 tokens / $0.016382。这么做的意义：成本任何时刻都能从日志复算——不会出现"账本和日志对不上"，也不需要在代码里到处埋计费变量。
边界（README 里明写，别改口径）：checkpoint 持久化的是状态，不是副作用。续跑只保证"已完成的工具调用不重放"，工具副作用是 at-least-once，不保证幂等——崩溃窗口里"写文件 / 下单"这类操作仍可能被执行两次。要做到副作用一致，得再加幂等键或"先写意图再执行"的补偿逻辑，那是下一步的事。

② rag-eval-platform — 模块化 RAG + 系统化评测

RAG三层评测策略对比

一句话：把"检索 → 生成 → 评测"三层解耦，每个环节可单独替换、单独度量、单独做对比实验。重点不是"能问答"，而是"能证明答得对不对"。

诚实标注的边界（必讲）：自带样例只有 5 篇文档，三种切分策略的文档级 recall@3 全部 1.0——这是"数据集太小导致的天花板效应"，不是"某策略最优"。实验报告里已如实写明，并给出扩到更大评测集的建议。面试被追问"为什么不选最优"时，这个回答比硬编结论更可信。

②-增强：混合检索（BM25 + 向量 RRF + 可选重排）

把"纯向量"升级为"双路召回 + 排名融合"。这不是炫技——是为了解决纯向量在近义/重复文档上把分数分散到多个副本、导致相关文档排不到前面的真实痛点。
怎么讲这坨（STAR）："纯向量检索对精确术语和近义副本不敏感。我加了 BM25 关键词路 + 向量语义路双路召回，用 RRF（按排名融合，而非加权求和，因为两路分数量纲不同）合并，并可接 Cross-Encoder 重排二次精排。为证明有效，我搭了两个评测集做对照：干净知识库上两者都接近上限，但含近义副本的噪声语料上，纯向量 recall@3 只有 0.625、混合拉到 1.0——这正好说明'何时该上混合检索'。用 retrieval.mode 开关切换，默认纯向量保证零回归。"

本版新增：六档位实测（质量 × 延迟，含负结果）

把 纯向量 / 纯 BM25 / 混合 RRF / +重排 / +multi-query / +HyDE 六个档位在同一口径下跑完（文档级 Recall@3 / MRR，延迟是单次 _retrieve 的热启动 p50，不含生成回答），并把延迟一起记账。评测集两套：realistic（14 篇，话题区分度大）与 near_dup_stress（10 篇，含大量近义副本的噪声库）。

口径备注：延迟为单机实测的热启动 p50（含查询编码 + 检索 + 重排/改写，不含生成回答），重排与改写档位存在运行间波动，量级可信、具体数字不宜当基准线；质量指标（Recall / MRR）是确定性的、可复现。

两个必须主动讲的诚实结论（负结果比正结果更能证明会做实验）：
  • ① 多路召回不等于更好：噪声库上纯 BM25 的 MRR = 1.0，反而高于混合 RRF 的 0.7708——混合把召回拉满了，但 RRF 按排名融合会牺牲头部精度；换句话说，"上一路 BM25"在近义副本场景里本身就够了，加向量的融合规则反而是负优化。
  • ② HyDE 在噪声库掉点：R@3 1.0 → 0.75，而热 p50 从毫秒级涨到 5.6s（约 ×13000）——改写收益依赖生成模型质量，小模型生成的"假想文档"会把噪声一起召回。
  • 所以：重排 / 查询改写做成默认关、按场景开——收益不确定（干净库上召回满分时它只能改排序），代价确定（延迟 ×百倍）。开之前先问一句"召回还有没有提升空间"。
怎么讲（一句话版）："我把检索的六个档位在同一口径下跑了一遍，并且把延迟一起记账：+重排能把 MRR 从 0.9286 顶到 1.0，但要花 995ms；HyDE 在干净库上没有收益、在噪声库上反而掉到 0.75 且延迟 12.6s。所以我把它做成默认关——能证明"什么时候不该用"，比只会说"我上了高级技巧"更值钱。"

②-2 · 我不猜，我测了 —— 本地 1.5B 能不能当评测裁判

实测三方对照零成本规则主干负结果可复现

一句话：仓库里早就有"让本地小模型当 LLM-as-Judge"的实现和文档宣称，但一个实测数字都没有。这一节把它补上：同一批 33 条样本 + 同一份检索上下文 + 同一份 rubric，让规则判据 / 本地 Qwen2.5-1.5B 自评 / 强裁判 API 三方各判一遍，再比它们彼此有多一致。结论先说：本地 1.5B 在这个任务上不适合作裁判——与强裁判几乎零相关（r −0.0326）、MAE 1.8182，而且偏差是系统性的中庸化回归，它能胜任的只是两端粗筛。反过来，零成本的规则判据比它更贴近强裁判（r +0.5890、MAE 0.9152）。

为什么这条值得花时间修：它原本属于典型的「有实现、有文档宣称、零实测数字、零测试覆盖」——代码能跑、README 写着支持三维打分，可面试官一句"faithfulness 多少分"就答不上来。修它的价值不在于"多一个功能"，而在于把一句宣称换成一次测量：现在它有数字、有口径、有边界，还能离线复跑。

读法：精确一致 = 分数完全相同；±1 一致 = 差一分以内；MAE 越小越好，r 越接近 1 越好。只报平均分会骗自己——中庸化的裁判"看起来均分还行"，但排序信息已经丢了，所以必须看 r，并且按档位分段看。

支撑检查（这条不改变上面的主结论）：同一口径在另外两个维度上再算一遍——臂 B vs 臂 C，n = 33，看"零相关"是不是 faithfulness 一个维度的偶然。

连上主表的 faithfulness（−0.0326）：三个维度的 Pearson r 全部落在 |r| < 0.1——"几乎零相关"不是某一个维度的偶然，而是三个维度上一致出现的现象；三个维度的 MAE 都在 1.67–1.82（1–5 量表上，平均差接近两档），连偏差幅度都一致。
边界（别顺手扩大）：臂 A 只有 faithfulness 有 1–5 粗分，另两维是 EM/F1/ROUGE 这类词法指标、量纲不同，所以 A vs C 只对 faithfulness 有意义——另外两维没有 A 的相关系数可报；而且这依旧是两裁判一致性，不是与人类标注对齐，强裁判本身也不是真值。

为什么"零相关"不是随机抖动，而是系统性的中庸化回归

最该抓的样本，被放行了：unanswerable#2 —— 问题在知识库里没有答案，正确答案就是"不知道"，模型却编了一份川菜菜谱。本地裁判给 faithfulness / relevance / completeness = 3 / 5 / 3，强裁判给 1 / 1 / 1：三个维度全被判成"及格"。这就是中庸化回归的真实代价——它不会说"这条错得离谱"，只会说"还凑合"；而 RAG 的幻觉恰恰要靠"离谱"这个信号才拦得住。
方法论：结论不是"我觉得 1.5B 不行"，而是三件事
  • 同批样本、同 rubric、同上下文：33 条样本、三臂共用同一份检索上下文，答案由 Qwen2.5-1.5B-Instruct 在 temperature=0 下贪心生成——换个人回来跑，拿到的是同一批答案，比较才有意义。
  • 算一致率矩阵，而不是各打各的分：精确一致 / ±1 一致 / MAE / Pearson r 四个口径一起看。只报"平均分"最容易被中庸化骗过去：均分能对上，排序全反了。
  • 确定性规则打主干，强裁判只做交叉验证：规则判据（数字/实体落地率、句子归因的字符 2-gram 覆盖率 ≥ 0.6、拒答判定、EM/F1/ROUGE-L/BLEU → 1–5 粗分）零成本、可重复，能进 CI 门禁、每次提交都跑；强裁判只在这 33 条上做对照，整轮 ¥0.0232。贵的只用来校准便宜的，不让它变成日常依赖。
成本与可复现（这两条是"敢报数"的前提）：29 次新调用 + 4 次缓存命中，输入 19,248 tokens / 输出 638 tokens，合计 ¥0.0232；预算硬上限 ¥0.5，超了就停——省钱靠代码，不靠"记得省着点"。
贪婪解码 + 磁盘缓存，离线复跑逐条一致、不一致数 0：这组数字不是"某天跑出来的样子"，而是谁都能重跑出来的结果。
能力证据的诚实边界（这段必须照实讲）：
  • 人类标注只有 5 条，且只用来校准规则阈值——它不构成"与人类对齐"的评测。
  • 规则判据已知 5 类误判：改述但无字面重叠 → 误判"未归因"；模板化句式 → 误判"已归因"；落地率只看"出现过"、不看"用对"；拒答是字面标记匹配；1–5 本身是粗映射。
  • 只做了两裁判一致性，不是与人类标注对齐；强裁判本身也不是真值，它只是更贵的参照系。
  • 本节所有数字都是每样本单次调用（N=1）；N>1 已于 2026-10-20 补测（N=7）：单个「样本 × 维度」的抽样标准差约 0.41 档（faithfulness；relevance 0.32、completeness 0.29），7 次采样只有 38.4% 完全一致、99 个单元里有 24 个摆动 2 档（这是 7 次全同的口径，观测次数更多、标准更严，不能和下面 N=3 的 71.7% 直接相减）；中位数聚合把 MAE 的抽样 sd 从 0.087 压到 0.062（N=7，−29%；N=3 只降 14%），但结论方向不变——median-of-7 下 r = −0.1436、MAE = 1.9394，仍近零相关、仍远差于零成本规则臂的 0.9152，且 unanswerable#2 的 faithfulness 反而从 3 抬到 4。所以这组数字有量级意义，但没有小数点后四位的精度。
  • 参照系本身也做过稳健性检验（2026-10-20，强裁判 API 侧 N=3）：上面所有结论都是拿"单次调用的强裁判"当参照系算的——如果参照系自己在飘，结论就得打折。所以我把强裁判也跑了 N=3（99 次新调用、¥0.0777、零兜底、答案与原批次逐条相同），用 3 次采样的中位数当新参照系重算：本地 1.5B 仍是近零相关（r −0.1595、MAE 1.9394），零成本规则判据仍明显更贴近（r +0.5485、MAE 1.0061），"中庸化回归"依旧成立（判低组本地 3.400 vs 参照 1.400、判高组 3.037 vs 4.889）。同时实测到强裁判不是零噪声：3 次采样只有 71.7% 完全一致、99 个单元里有 3 个摆动 ≥3 档（严格同 N 的对照：同一次运行里本地裁判 N=3 时是 55.6%）；但它与自己 N=1 参照的 MAE 只有 0.11 档、r +0.92 —— 所以两个裁判的分歧不是参照系噪声造成的。
  • 中档 (3) 的样本数 n=0，中间档的区分力无法评估（如实标注，不假装测过）。
怎么讲（一句话版）："我不猜，我测了——同一批 33 条样本、同一份 rubric，把规则判据、本地 1.5B 自评、强裁判摆在一起对照：本地 1.5B 的 faithfulness 与强裁判几乎零相关（r −0.0326、MAE 1.8182），而且不是抖动、是中庸化回归——低档 6 条被抬到 3.167（强裁判 1.667）、高档 27 条被压到 3.111（强裁判 4.852），最该抓的拒答样本被判成 3/5/3。而且我把参照系本身也换成 3 次采样的中位数重算了一遍，主结论照样不变（本地 r −0.1595 / MAE 1.9394，规则臂 r +0.5485 / MAE 1.0061）——分歧不是参照系噪声造成的。反倒是零成本的规则判据更贴近强裁判（r +0.5890、MAE 0.9152）。所以我的结论是分工：规则判据进 CI 当主干，强裁判只做小样本交叉验证（整轮 ¥0.0232），本地 1.5B 只用于两端粗筛。这不是"1.5B 不行"，是位置放错了。"

③ rag-mcp-server — 把检索封装成标准 MCP 服务

MCPstdio + HTTP可复用鉴权 + 限流(新)注入防护(新)/healthz + /metrics(新)

一句话：用官方 MCP SDK 把同一套 RAG 检索链路暴露成标准工具，本地用 stdio、远程用 Streamable HTTP，Claude Desktop / Cursor / 自己的 Agent 都能直接调用，一次实现处处复用。本版再补上"能给别人用"的那一层：鉴权 / 限流 / 探针 / 指标 / 检索结果注入防护。

两个真实且可讲的坑：① stdio 模式下 stdout 是协议通道，一行 print 就会破坏报文——日志一律走 stderr；② 客户端用 mcp 1.x、服务端用 mcp 2.x，能互通是因为"互操作依据是协议本身、不是 SDK 版本"。这俩都是面试里的加分细节。
增强：双传输（stdio + Streamable HTTP）——本地宿主由客户端拉起子进程走 stdio；远程/多客户端则起 HTTP 服务，端点是 /mcp。关键点是只换传输层、不动检索代码：server.py 把同一组 tool 挂到不同 transport，KnowledgeService 完全不知道 MCP 的存在。还处理了两个生产细节：① 默认只绑 127.0.0.1，避免把无鉴权服务暴露公网；② 用域名/IP 对外访问时显式配置 DNS rebinding 的 allowed_hosts / allowed_origins，否则会被 421 拒绝。新增 8 个测试，其中 1 个是真起 server 子进程 + 官方客户端走完整 HTTP 协议的端到端验证。

本版新增 ③-1：HTTP 生产化 —— 从「能跑」到「可运维」

这一层的关键不是"加了个中间件"，而是顺序和豁免白名单是刻意设计的：限流排在鉴权之前，探针路径排在鉴权限流之外。
① 鉴权（Bearer）：无 token → 401 + WWW-Authenticate；错 token → 401；正确 token 通过并成功调用 search_knowledge。token 比较走常量时间比较（不给"按响应时间猜 token"留缝）；配置里写了 auth.enabled=true 却忘了给 token → 启动即报错（fail fast），绝不静默放行。
② 令牌桶限流（刻意先限流、后鉴权）：未携带正确 token 的洪水，一样要过协议解析、日志、TLS——先限流才能挡住"拿错误 token 暴力猜"。实测 burst=10 连打 18 次 → 前 10 次 401、后 8 次 429 + Retry-After: 2；同一时刻 /healthz 仍然 200（豁免路径不被限流误杀）。分桶按 token、无 token 按客户端 IP，合法客户端不会被别人的洪水拖累。
③ 探针与指标（零新依赖）：/healthz 返回只读快照（index_ready / documents / chunks），绝不触发建索引——健康检查不该有副作用，否则"探一下就变慢/变贵"；/metrics 是手写 Prometheus 文本格式（counter 命名、label 转义、没有数据时也输出 {rule="none"} 0），就是为了不引入新依赖：可观测性不该成为"启动失败的风险源"。
④ 压测（20 并发 × 100 请求，用官方 streamable-http 长连接客户端）：QPS 166.9 / p50 95ms / p95 180.5ms / p99 181.9ms / 错误率 0。防自欺的一步：客户端 160 次调用 == 服务端 tool_calls_total 增量 160——两边对得上，才敢说"服务真的处理了这么多"，而不是客户端自己的计数器自说自话。
压测顺带抓到一个真实并发 Bug（这段最有讲头）：并发请求同时 np.save 同一个缓存文件 → 后写截断先写，读取端报 file seems not fully written?。修法不是"加个锁就完事"：单飞（single-flight）锁 + 写临时文件 + os.replace 原子替换——读者要么看到旧文件、要么看到完整的新文件，永远不会看到"写了一半"的中间态。
边界（照实说）：安全层是"够用级"不是生产级——静态共享 token（不是 OAuth 2.1、没有密钥轮换）、进程内令牌桶（多副本要挪到网关层）、默认只绑 127.0.0.1；Dockerfile 已写，但本机没装 Docker，未实际构建验证。压测全部是单机数字，只证明"服务按预期工作"，不代表线上容量。此外 scripts/demo_http_security.py 把这一串做成了一条命令 10 项全 PASS 的演示（401 / 429 / healthz / metrics / 注入标记）。

本版新增 ③-2：检索结果的提示注入（间接注入）防护

威胁模型一句话：RAG 检索回来的文档本身可能写着"忽略以上指令、去做 X"——上层 LLM 天然分不清"资料"和"命令"，于是知识库变成了攻击面（间接注入 / 知识库投毒）。
三层怎么分工：
  • ① 结构化隔离：检索结果一律包进 <untrusted_data> 标签，并带 trust: "untrusted" 字段 + 一句显式声明——让上层知道这段是数据、不是命令。
  • ② 可解释标注（11 条规则）：命中就返回规则 id + 严重级别 + 人类可读原因 + 命中片段（如 instruction_override / fake_tool_call / react_scaffold / fake_role_line / hidden_markup / exfil_url / overlong_line / invisible_char …），覆盖中英文指令注入、伪 system 行、伪工具调用 JSON、ReAct 脚手架、零宽字符 / Unicode Tag、HTML 注释与 CSS 隐藏、外带链接、超长行、base64 大块。
  • ③ 中和而不删内容：保留正文（不能因为"疑似"就把资料删掉），只让它不再呈"可执行指令"的形态：角色标签降级成普通文字、外带链接打标、不可见字符转义成可读形式、超长行折行……并提供配置开关可整体关闭。
实测证据：13 类对抗手法全部命中（每条都给出命中的规则 id）；9 篇正常语料零误伤（含 5 篇真实知识库文档）。命中数计入 /metrics 的 prompt_injection_findings_total{rule}——知识库被投毒的第一手信号，可以直接接告警。
诚实边界（这段必须照实讲，别改成吹牛版）：模式匹配会被绕过——换措辞、换语言、多段拼接、把指令藏进图片/附件都能绕开；它也会误报（讨论注入的文档、大块 base64 都会被标）。所以它的定位是抬高攻击成本 + 给上层提供判断依据，不能替代上层 Agent 的信任边界与工具权限控制——这句话本身就是加分项。

CI 门禁（GitHub Actions）

五个仓库都有 .github/workflows/ci.yml，四件事是想清楚的：
  • 离线可跑：HF_HUB_OFFLINE=1 + TRANSFORMERS_OFFLINE=1，让"缺模型"变成硬失败——而不是在 CI 上静默联网下载几百 MB，把"绿"建立在一个没人看过的网络请求上。
  • 需要真实 BGE 模型的用例显式排除：用 --deselect 列出清单（不改测试源码），本地全量 173 passed，CI runner 上是 160 passed（13 个用真实 BGE 模型的用例显式排除）。
  • 回环用例的代理坑：NO_PROXY=127.0.0.1——机器上挂了全局代理时，连 127.0.0.1 的请求也会被转发（本机实测回 502），会让回环用例误报失败。
  • 踩过并修掉的真实坑：NO_PROXY 与 no_proxy 只差大小写，GitHub 的校验器把它们当重复键 → 整个 workflow 文件被判无效（run 在 job 起来前就失败、且不可重跑，本地 YAML 解析却完全正常）。两个仓同时中招，定位方法是「临时探针仓逐变体二分」。
  • Gitee Go 也接了：各仓的 .workflow/MasterPipeline.yml 跑的是与 GitHub Actions 完全同一批命令（含同样的排除清单）——两边口径一致，任何一边红了都能在另一边复现，不会出现「是不是环境不一样」的推诿。
  • 文档数字不许漂移：每个仓都有「数字自检」——README 里引用的每个数字必须能从 results/ 的产物重算出来，对不上就 CI 报错。求职助手那边还升级成带语境断言：数字必须出现在它该在的那句话里（否则「124 条」这种错值会因为 123 在表格别处出现过而蒙混过关）。
诚实标注（必须说清）：五个仓库都同时托管在 Gitee 与 GitHub（同一份历史、同一批 commit SHA），而且两边都接了自动门禁：GitHub Actions（每次 push / PR 自动执行，README 顶部的徽章是真跑状态，五个仓全绿）＋ Gitee Go（.workflow/MasterPipeline.yml，同一批命令、同一套口径，含同样的 --deselect 排除清单，每次 push 到默认分支自动构建）—— 五个仓在 Gitee 侧也全部构建通过。Gitee 侧的构建记录在仓库页「流水线」里，需要登录才能看到 —— 所以 Gitee 侧不挂徽章（匿名访问会被登录墙挡成 404，挂一个坏徽章比不挂更糟）。另外三个真实边界：① GitHub 的 workflow 校验会把「只差大小写的 env 键」当重复键——本项目一度同时写了 NO_PROXY 与 no_proxy，导致整个 workflow 文件被判无效（run 在 job 起来前就失败、且不可重跑）；这个坑已修并写进注释。② 有 1 个用例需要真实 BGE 模型 + GPU（tests/test_pipeline.py::test_embedding），CI 上用 --deselect 在命令行显式排除（不改测试源码），汇总行会报 1 deselected——配额对不上就是配置漂了。③ Gitee Go 的 YAML 与 GitHub Actions 方言不同，且键名大小写敏感（写错不会在文件里报错，而是流水线直接不生效），触发器前缀还必须跟各仓的默认分支对上（job-fit 是 main、其余是 master —— 对不上就「推了但没有构建历史」）。

新增能力的追问速查（六问 + 一句答法）

追问一句答法（都能指到命令/文件）
为什么限流要排在鉴权前面？没带正确 token 的洪水同样吃 CPU（协议解析/日志/TLS），先限流才挡得住"暴力猜 token"；探针路径豁免，所以限流期间 /healthz 仍 200，编排不会误判服务已死。
/metrics 为什么不用 prometheus_client？手写 Prometheus 文本格式就够用，零新依赖——可观测性不该变成"启动失败的风险源"；label 转义、空值输出都按格式规范处理过。
注入防护为什么用"中和"而不是"删掉"？删内容等于替用户做了内容裁决，还可能把合法文档删掉；中和只让它不再呈"可执行指令"形态（角色标签降级、外带链接打标、不可见字符转义），并有开关可关。
你的防护能挡住注入吗？不能，只是抬高成本：换措辞/换语言/多段拼接/藏图里都能绕；它给的是"命中规则 id + 严重级别"这样的判断依据，信任边界仍在最上层 Agent。
断点续跑会不会重复执行工具？已完成的不重放（实测重放步数 0），但副作用是 at-least-once、不保证幂等；要一致就加幂等键，这条 README 里明写了。
为什么不默认开重排 / 查询改写？实测收益不确定、代价确定：干净库上召回已经满分，重排只能改排序却要 995ms；HyDE 在噪声库反而掉点（R@3 1.0→0.75，延迟 ×13000）。所以默认关、按场景开。

诚实边界（说出口就失实，千万别讲）

  • ❌ "上线 / 生产 / 有用户量 / 能扛 QPS"——这是个人项目，没有部署。压测的 QPS 166.9 是本机单机数字（20 并发 × 100 请求），只证明"服务按预期工作"，不代表线上容量。
  • ❌ "安全层是生产级 / 我的防护能挡住注入"——安全层是"够用级"：静态共享 token（不是 OAuth 2.1、没有密钥轮换）、进程内令牌桶（多副本要挪到网关）、默认只绑 127.0.0.1；Dockerfile 已写但本机未装 Docker，没构建验证过。注入防护是模式匹配，会被绕过、也会误报，只能抬高攻击成本 + 给上层依据，不能替代上层 Agent 的信任边界。
  • ❌ "断点续跑 = 副作用幂等"——checkpoint 持久化的是状态：续跑只保证"已完成的工具调用不重放"（实测重放步数 0），工具副作用是 at-least-once，不保证幂等，崩溃窗口内写文件/下单这类操作仍可能执行两次。
  • ❌ "高级检索技巧一定更好 / 混合检索是银弹"——负结果照实说：噪声库上纯 BM25 的 MRR(1.0) 反而高于混合(0.7708)；HyDE 在噪声库掉点（R@3 1.0→0.75、延迟 ×13000）。重排 / 改写默认关：收益不确定、代价确定。
  • ✅ "CI 在自动跑"——这条现在是真的，而且两边都跑：五个仓库都镜像到 GitHub（Actions 每次 push / PR 自动跑测试，workflow 全绿、徽章是真跑状态），同时每个仓都接了 Gitee Go（.workflow/MasterPipeline.yml，同一批命令、同一套口径，每次 push 到默认分支自动构建）。要补两句边界：Gitee 侧的构建记录要登录才能看到（所以那里不挂徽章），且有 1 个用例因需要真实 BGE 模型 + GPU 被 --deselect 排除（汇总行报 1 deselected）。
  • ❌ "做了工具选择准确率的正式评测"——现在有了（新增 eval_harness），但样本是 16 条固定 query，讲清"是 smoke 级量化、非大规模基准"；而且这个指标我拆成了严/宽两个口径（严＝工具真的成功执行过），报的时候要说明用的是哪个。
  • ❌ "我的 LLM-as-Judge 是可靠裁判 / 本地小模型也能打分"——本地 1.5B 在本任务上不适合作裁判：与强裁判的 faithfulness 几乎零相关（r −0.0326、MAE 1.8182、精确一致 0.2121），且是系统性的中庸化回归（低档 1.667 → 3.167、高档 4.852 → 3.111，两端都往 3 分收），拒答样本 unanswerable#2 被判成 3/5/3。它的适用边界只有两端粗筛。零成本规则判据反而更贴近强裁判（r +0.5890、MAE 0.9152），主干该用它。
  • ❌ "两个裁判一致 = 评得对 / 这个评测已经和人类对齐"——人类标注只有 5 条，且只用于校准规则阈值；只做了两裁判一致性，强裁判本身也不是真值；本报告每样本单次调用（N=1）（N=7 方差补测：中位数把 MAE 抽样 sd 降 29%，但结论方向不变；参照系侧 N=3 稳健性补测：把强裁判换成 3 次采样中位数当参照系重算，主结论照样不变，所以分歧不是参照系噪声造成的）；中档 (3) 的 n=0，中间档区分力无法评估；规则判据还有已知 5 类误判。所以这组数字是"一致性证据"，不是"正确性证明"。
  • ✅ 已经能讲的（别再说"还没做"）：跨任务记忆、工具并发、上下文压缩、量化评测、断点续跑、用量核算都做了；我还审计过自己项目的指标，抓出过一个"假绿"并修掉了——领域外诚实率原本会把"模型调用失败、什么都没答出来"的运行算成"诚实拒答"（诚实率能刷到 1.0），现在只统计真正完成的运行并把分母一起报出来，配了回归单测；评测层那次"裁判分全部退化成启发式分却看不出来"的 bug 也是我自己挖出来修的。仍然没做的是多 Agent 协作、流式输出、真正的部署。
  • ✅ 加分项：大方承认参考了官方 ReAct 范式与 MCP SDK，但设计取舍（步数语义、四档失败、双形态 RAG、trace 字段、鉴权/限流顺序、注入"中和不删除"）是自己定的，每一步能指代码行。
